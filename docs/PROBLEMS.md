## Движки

- **Gemini CLI не подошёл.** С 18.06.2026 не обслуживает подписки Google AI Pro и бесплатный тариф
  (`IneligibleTierError`, код выхода 55). Проверено на реальном аккаунте. В headless-режиме ещё мешали «доверенные папки»
  (нужен `--skip-trust`) и `node` вне `PATH` у GUI-приложений.
- **Antigravity CLI (`agy`) тоже.** Замена Gemini CLI отказывает аккаунту по стране (`Eligibility check failed`).
  К тому же пишет файлы в рабочую папку по умолчанию, изоляция слабее, чем у `claude`.
- **Итог:** основной движок Claude Code по подписке Pro, запасной — локальная Ollama. Gemini можно подключить только по ключу AI Studio (`GeminiEngine`, 2026-11-04): подписка Google AI Pro (в том числе бесплатная от Jio) через сторонние приложения не работает, а использование OAuth-входа CLI из приложения запрещено условиями Google.
- **Gemini по ключу: бесплатные квоты нестабильны.** Свежие модели (3.7, 3.8 Flash) отвечали 429 и 503, 3.5 Flash завис на запросе с картинкой, Pro недоступна. Стабильно отвечает только Flash-Lite; движок сам переходит на неё.
- **Локальная модель слабее.** Qwen3.5-9B на плотном почерке: ошибка по символам 10–28%, 30–70 с на страницу.
  Поэтому всё, что сделала локальная модель, помечено «проверьте». Модели покрупнее на 16 ГБ не помещаются без потери качества.

## Что узнали по дороге

- Не доверять памяти о флагах CLI: каждый флаг сверяется с `--help` и пробным запуском ([`cli-notes.md`](cli-notes.md)).
- Правило «ничего не угадывать» оказалось слишком жёстким для плотного почерка: догадка с пометкой `[?слово]` полезнее, чем дыра.
- На мелком тексте помогает не одна страница целиком, а перекрывающаяся сетка фрагментов (режим «Подробно»).
- Расход лимита важен: улучшения, которые добавляют вызовы или картинки в промпт (страницы учебников картинкой, проверяющие проходы), владелец отклонил; рабочие решения идут локально (проверка конспекта, шпаргалка, чистка выдержек).
- Обычный Claude в чате видел фото целиком и писал заметно лучше «переписчика» (страница → текст → очистка без права менять слова): точная сборка осталась как режим, а по умолчанию модель смотрит на фото сама.
- Большинство учебников в `Documents` оказались сканами без текстового слоя; Vision читает их быстро (около 6 страниц в секунду), поэтому индекс строится за минуты, а не за часы.
- Синтетика («рукописный» шрифт) почти не отличает хороший результат от плохого: нужны реальные фото.
- Работа с файлами в iCloud: любое чтение вне фона может зависнуть на выгруженном файле.
- На macOS нет системного Dynamic Type: `dynamicTypeSize` не меняет кегль, `.body` не следует размеру текста
  в Универсальном доступе (проверено на macOS 26). Размер текста для чтения приложение задаёт само.
- Трёхколоночный `NavigationSplitView` на macOS 26 не выполняет `columnVisibility: .detailOnly`: колонки не прячутся.
  Режим повторения поэтому сделан слоем поверх окна.
- WKWebView не рисует, пока окно закрыто другими окнами (`document.visibilityState == "hidden"`): снимки фонового окна
  выходят с пустым конспектом, хотя страница загружена. Для снимков окно поднимают наверх (`window.level = .floating`).
- Пункт меню с `keyboardShortcut("+")` ловит только ⌘⇧=; ⌘= без Shift нужно ловить отдельно (скрытая кнопка).
- PDF после печати WKWebView: PDFKit записывает адрес ссылки как имя `##1` вместо страницы (ссылка никуда не ведёт)
  и не записывает закладки. Ссылки и закладки ставятся через CoreGraphics (`addDestination`, `setDestination`,
  `CGPDFContextSetOutline`) при перерисовке с колонтитулами. Перезаписывать PDF поверх того, из которого PDFKit
  его прочитал, тоже нельзя: изменения теряются.
- CoreGraphics пишет адрес ссылки отдельным объектом (`/Dest 188 0 R`). На Mac это работает, а «Файлы» на iPhone
  и Google Диск такие ссылки игнорируют. `PDFLinkInliner` подставляет массив адреса прямо в ссылку и пересчитывает `xref`.
- Системный шрифт SF в текстовом слое PDF отдаёт букву «к» как «ĸ» (U+0138): поиск «скаляр» не находит «сĸаляр».
  `PDFNavigation` ищет текст в обоих написаниях.
